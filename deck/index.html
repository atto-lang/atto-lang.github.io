03 / THE REAL COMPETITIVE FRAME

AttoPL is Erlang
+ Rust

Our first goal is to supplant runtimes like Erlang/Elixir, Java, Node.js, Golang, and Python for backend services by combining Erlang-style fault isolation with Rust-style ownership and borrow checking. Atto will be especially competitive for stateful (not stateless) backend services. As Atto progresses, competing as a systems language for long-running processes is a goal.

BORROW FROM RUSTMemory ownership

Static borrow and lifetime analysis, explicit control over data movement, and strong compile-time boundaries.

LEARN FROM ERLANGActor resilience

Mailbox semantics, per-actor state, supervision, fault containment, and live long-running services.

ATTO'S GOALCombine both

Actor-first design with mostly GC-free native runtimes, while preserving fault isolation and productivity.

Zero/near-zero GC and equivalent fault tolerance are goals, not universal claims about current backends.

04 / CONCURRENCY

Many threads.
One safety model.

Like Erlang, AttoPL is designed with separate heaps and stacks per actor for fault isolation and easier hot swapping. The Atto borrow checker aims to support multiple threads in the main control flow and within actors, including parallel message processing with checked state access.

05 / EXECUTION STRATEGY

Actor ergonomics.
Native-code ambition.

Atto is targeting AOT-native execution for major runtimes, with selective JIT and hot-loading strategies where they provide value.

BEAM is not simply “interpreted”: Erlang/OTP includes a native-code JIT. Performance depends on workload; no benchmark win is claimed here.

07 / OPINIONATED BY DESIGN

Things we want to
move beyond.

Two deliberately provocative examples: React and Python. Not because they never work — because their tradeoffs aren't our defaults.

R

React

Complex state orchestration, rendering coordination, and a heavy client application toolchain can obscure the underlying domain model.

Atto direction: stateful actors as a clearer unit of composition.
Py

Python

Dynamic checks and runtime overhead are often the wrong fit for systems-level, highly concurrent services.

Atto direction: compiled contracts and explicit concurrency.

This is a statement of design taste, not a universal performance or usability judgment.
