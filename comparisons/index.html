Type systemBrowser example

Static types and local inference are design foundations. The pinned browser profile admits typed control flow, traits/interfaces and data shapes; generic and refinement coverage varies.

Run admitted example		Dynamically typed Erlang terms with pattern matching, optional typespec annotations and Dialyzer success typing. These give useful inferred analyses but do not turn Erlang into a gradual static type system with guaranteed compile-time checks.Statically typed with strong local type inference, nominal types, traits, generics and exhaustive enums. Inference removes many annotations without weakening static checks; ordinary Rust does not provide gradual dynamic typing.OCaml/Gleam use inferred static types; Go infers some declarations; Python typing uses Any as a gradual form while its runtime stays dynamic. TypeScript offers gradual-style adoption around any/unknown and JavaScript interop, with limitations.
Hot reloading in productionResearch / not established

Generation fencing, quiescence, state migration and rollback are goals. No production-safe live actor upgrade certification is claimed.

OTP supports versioned module loading and release upgrades, with upgrade scripts and state migration; some VM upgrades require restarts.No language/runtime-wide hot code replacement; rolling restarts, dylib/plugin designs or process handover are typical.Elixir inherits BEAM upgrades; JVM/.NET offer limited hot-swap/reload tooling, not universal stateful production upgrades.
Build systemDesign / in development

Compiler tooling and multi-backend packaging are evolving; no Cargo-equivalent maturity or reproducible cross-backend build guarantee is asserted.

erlc and OTP releases; rebar3 and Mix (Elixir) organize builds and dependencies.Cargo provides dependency resolution, builds, workspaces, testing and packaging; rustc compiles crates.Go toolchain/modules, Gradle/Maven, CMake/Meson and dotnet build are established alternatives.
Borrow checkingBrowser example

Explicit borrow/copy/take/share operations; a narrow executable borrow example and independent flat-class copy!! are admitted. Transitive loans, lifetimes and suspension safety are not established by these examples.

Run admitted example		No compile-time affine ownership or borrow checker; actors exchange immutable terms and use process isolation.Compiler-enforced ownership, shared/mutable borrowing and lifetime checking, including across async contexts.C++ has RAII without Rust-equivalent universal borrow checks; Swift enforces some exclusivity rules.
Memory safetyDesign / in development

Ownership, checked operations, actor isolation and validated FFI boundaries are intended safety mechanisms. No all-backend memory-safety certification or freedom from runtime faults is claimed.

Ordinary BEAM terms are managed and isolated by processes, preventing many pointer and lifetime errors in Erlang code. Native implemented functions (NIFs), drivers and ports have different trust and failure boundaries.Safe Rust enforces ownership, borrowing and bounds checks to prevent many memory errors; unsafe Rust, native libraries and FFI still require manually upheld invariants. Memory safety is not a guarantee of logic or availability safety.Java, C# and Go provide managed memory safety with escape hatches; C/C++ provide low-level control but generally require additional discipline and tooling.
Garbage collectionDesign / in development

Actor-owned regions and zero guest tracing-GC are targets for selected profiles. Host runtimes may use GC; neither zero total allocation nor zero host GC is claimed.

BEAM normally performs garbage collection on individual process heaps; large binaries can be shared via reference counting.No mandatory tracing GC; deterministic drops/RAII, ownership, and reference-counted options such as Arc.Go, Java, C# use managed GC; C/C++ use explicit/RAII lifetime strategies.
32-bit pointers / compressed arena offsetsResearch / not established

Research target: store checked 32-bit offsets or handles into actor-owned regions no larger than 4 GiB, with bounds, alignment and generation validation. A 64-bit process still uses native-width pointers at FFI/OS boundaries. Savings and overflow safety require proof.

Term and pointer representation depends on the BEAM build and target word size. A 64-bit BEAM is not a universal 32-bit-pointer or compressed-reference system; term tagging and shared binaries affect real memory use.Native pointers follow the target architecture (32-bit target: generally 4-byte thin pointers; 64-bit target: generally 8). Applications can explicitly use u32 indices/relative offsets in bounded arenas; Rust does not automatically compress arbitrary pointers.JVM compressed ordinary object pointers may reduce reference footprint; WebAssembly wasm32 uses 32-bit linear-memory addressing; C/C++ can implement compact handles manually. Object/layout overhead can outweigh pointer savings.
Soft real timeDesign / in development

Target: bounded actor admission, fairness, preemption checkpoints and runtime backpressure; latency SLOs need measured proof.

BEAM reductions, per-process scheduling and supervision make soft-real-time I/O a well-established strength; no fixed deadline guarantee.Can achieve low latency with async runtimes or dedicated threads, but scheduling and allocation require deliberate engineering.Go, Java and .NET support latency-sensitive services with tuning and observability.
Hard real timeResearch / not established

Not certified: a restricted, bounded-allocation native subset and RT kernel integration would require WCET/interrupt/scheduler verification.

General BEAM/OTP is not a hard-real-time platform and does not certify worst-case deadlines.Possible on suitable RTOS or real-time Linux with bounded code and audited dependencies; Rust alone guarantees no deadline.C, C++, Ada/SPARK and RTOS toolchains are established in hard-RT domains; PREEMPT_RT helps but is not a universal guarantee.
AOT vs JITBrowser example

The pinned browser compiler emits guest WebAssembly. Native AOT/JIT choices for other backends must be verified separately; Wasm generation is not proof of a native executable.

Run admitted example		BEAM bytecode is compiled ahead of running modules and OTP has a JIT in modern runtimes; not the same as producing standalone native programs.Usually AOT to native binaries via rustc/LLVM; no general-purpose production JIT in standard Rust.Java/.NET normally mix IL/bytecode with JIT and support AOT paths; Go usually compiles AOT.
Native code and standalone single binariesDesign / in development

Native AOT is a target for selected backends, with linking and host dependencies varying by profile. No claim of a standalone executable for every target.

Erlang modules execute on BEAM (with an OTP JIT on supported hosts). OTP releases can package an embedded runtime and dependencies, but standard deployment is not one self-contained machine-code executable.rustc normally emits native AOT executables and libraries; a single executable is often practical. Full portability or static linkage still depends on libc, target ABI, linked native libraries, assets and OS facilities.Go often produces a single native executable; C/C++ depend on linker/toolchain settings; .NET Native AOT and GraalVM Native Image can ship native binaries; JVM apps commonly need a runtime or bundled distribution.
Target architectures and portabilityDesign / in development

Browser source-to-Wasm is a published subset. Native LLVM, Java/GraalVM, .NET, Forge and other target profiles require independent target-level evidence.

OTP commonly targets x86-64 and ARM/AArch64 on supported operating systems; other CPU/OS combinations require platform-specific runtime builds and testing. Cross-compiling BEAM/ERTS is not the same as universal target support.rustc offers tiered target support for x86/x86-64, ARM/AArch64, RISC-V, WebAssembly and other CPU/OS triples. Standard-library availability, atomics, toolchain distribution and cross-linking differ by target tier.C/C++/LLVM and Zig have broad cross-compilation ecosystems; Go builds many CPU/OS pairs; Java and .NET target their respective supported VMs/runtimes. Availability must be checked for exact triples, not inferred from language names.
Usage in Lambdas / serverlessResearch / not established

Target: actor-backed functions in native/AOT builds and optional GraalVM modes; no verified AWS Lambda runtime, cold-start or cost advantage.

AWS Lambda can host Erlang/Elixir through custom runtimes or containers; BEAM startup and packaging remain factors.AWS Lambda supports Rust through custom runtimes/third-party tooling; native executables can benefit cold-start and memory budgets.Go, Java, Node.js, Python and .NET have mature Lambda ecosystems; language closures are a separate concept.
Mobile phones (Android / iOS)Research / not established

Target: native/AOT isolated actor components for Android and iOS with platform FFI and lifecycle integration, respecting battery, background limits and iOS code-loading policies. No complete signed mobile app/SDK path is verified.

BEAM can be embedded in mobile applications using specialized integrations, but Android/iOS app delivery, platform policies, startup and footprint require substantial adaptation; not a standard mobile UI workflow.Android and iOS cross-compilation are supported targets. Rust is often used for reusable native libraries and application backends, paired with Kotlin/Swift or cross-platform UI tooling; mobile packaging and platform SDK integration remain necessary.Kotlin/Java with Android, Swift/Objective-C with iOS, Flutter/Dart and React Native/JavaScript supply established mobile UI ecosystems.
Desktop applicationsResearch / not established

Target: LLVM-native or GraalVM-backed app services with supervised background actors, native GUI/WebView bindings and package/sign/update workflows. No complete production desktop UI framework or installer is verified.

Erlang/OTP runs on desktop platforms and provides wx bindings; GUI packaging and native desktop UX are less central to its ecosystem than server/telecom workloads.Native binaries target Windows, macOS and Linux; Tauri, egui, iced and Slint support desktop app architectures. UI frameworks, code signing, packaging and auto-updates are ecosystem choices.Electron (JS), .NET MAUI/WPF, Qt/C++, JavaFX and SwiftUI/AppKit offer established desktop application stacks.
Actor systemDesign / in development

Typed actor references, isolated mutable state, mailboxes and supervision are central design goals. The public profile identifies the older actor guest separately; full actor isolation, typed messaging and supervision are not proven by that demo.

Native lightweight processes, mailbox receive, links, monitors and OTP supervisors; battle-tested semantics.Actors are typically crates/frameworks (Actix, Ractor, etc.), not core language primitives; Tokio tasks are not actors.Elixir has OTP; Orleans provides virtual actors; Akka provides actor abstractions and cluster sharding; Go favors goroutines and channels.
Functional programmingBrowser example

Functions, lambdas, pipelines and lexical pure examples are admitted; broader effect guarantees require backend evidence.

Run admitted example		Functional-first, immutable binding, closures, recursion, comprehensions, and higher-order functions; mutation is not idiomatic.First-class closures, iterators, traits, pattern matching and functional combinators alongside imperative mutation.Haskell/OCaml emphasize functional typing; JavaScript, Kotlin and C# mix functional and imperative styles.
Algebraic data types (ADTs)Browser example

Data shapes, match and Result/Option are admitted in the pinned browser subset; arbitrary exhaustive matches and ownership/sendability are not established.

Run admitted example		Tagged tuples and pattern matching encode variants dynamically; records are tuple-based, not native Rust-style sum types.Enums with data-bearing variants, structs, Option/Result and exhaustive match form expressive static ADTs.Gleam/OCaml/Haskell have native sum types; TypeScript unions are erased at runtime.
Data-oriented programming (DOP)Browser example

The pinned browser profile admits i64 struct-array AoS, SoA and AoSoA(4) guests. General layouts, SIMD, GPU and comparative performance remain unverified.

Run admitted example		Erlang's immutable terms, binaries, ETS and batch-oriented message formats can represent collections, but BEAM does not natively expose explicit SoA/AoSoA memory layout or portable SIMD guarantees.Array/slice/struct layouts, iterators and explicit buffer ownership enable AoS, SoA, AoSoA and columnar data pipelines. Layout optimization is a programmer/library choice, not the default for every Rust collection.C/C++, Zig, Julia, Arrow and columnar database engines offer established data-parallel layout techniques; DOP refers to shaping programs around data transformations, not necessarily an ECS architecture.
Data-oriented design (DoD) / ECSResearch / not established

Architecture target: design around access patterns, hot/cold fields, AoS/SoA/AoSoA chunks, archetype-style ECS queries and actor/task affinity. Keep mutable chunks actor-owned and forbid uncontrolled shared writes; no verified cache-miss or ECS throughput win.

Can organize systems around transformation stages, data batches and ETS tables, but OTP processes/supervisors are not intrinsically an ECS or a cache-local component storage engine.ECS libraries such as Bevy ECS and hecs allow entity IDs, compact components and systems running over matching component sets; storage layouts and contention patterns depend on each ECS implementation.Unity DOTS/Entities and C++ EnTT are established ECS and data-oriented design systems. DoD is an architectural method about locality and data flows, distinct from the language's DOP expressions and types.
GPUsResearch / not established

Research: GPU buffer/layout contracts and accelerator offload integrated with typed data and actors; no general production GPU backend verified.

Typically offload through NIFs, ports, drivers or external accelerator services; GPU code is not built into Erlang.GPU via crates/frameworks such as wgpu and CUDA bindings; safety depends on device API and kernel language.Python has PyTorch/CUDA; C++ has CUDA/HIP; WebGPU is available across browser/native ecosystems.
Distributed systemsResearch / not established

Goal: ProxyActor, typed remote messages, capabilities and supervised transports over IPC/TCP/HTTP; cross-node parity unverified.

Built-in distributed Erlang, process messaging, node connectivity, OTP clustering/supervision patterns.Networking/RPC/serialization typically assembled using crates; distributed actor systems exist as libraries.Go has gRPC and cloud tooling; Java has Akka/cluster stacks; Elixir inherits BEAM distribution.
Carrier-grade LinuxResearch / not established

Target: supervised native Linux actors, graceful upgrade/rollback, failure isolation, bounded queues and diagnostics. No independent CGL compliance, carrier-grade availability target or telecom certification has been demonstrated.

OTP has a long telecom deployment history, with supervision and distributed application patterns on Linux. Carrier Grade Linux concerns system availability and conformance; Erlang/OTP alone is not a CGL certification.Rust native services can run on HA Linux deployments and integrate with watchdogs, redundancy and RT scheduling. Safety and carrier-grade availability require system design, fault-injection and operations evidence.C/C++, Java, Erlang and Go services can all participate in carrier-grade Linux deployments; hardware, kernel, redundancy, monitoring and operational qualification are system-level concerns.
Embedded systemsResearch / not established

Research direction: freestanding LLVM/AOT language subset with static/arena allocation and explicit peripheral/C ABI bindings; full actor scheduler and networking need a suitable host. No validated microcontroller firmware target is claimed.

BEAM can run on capable embedded Linux/RTOS devices and purpose-built platforms such as GRiSP. Small microcontrollers with very limited RAM/flash generally cannot host a standard BEAM runtime.A mature embedded ecosystem targets Cortex-M and other MCUs through no_std, embedded-hal, target-specific crates and RTOS/firmware integration. Capability depends on target and board support.C/C++ and Ada/SPARK are established in embedded firmware; Zig and MicroPython cover different resource budgets.
FPGA and ASIC integrationResearch / not established

Long-term research: actor-supervised CPU control planes plus typed device buffers and explicit accelerator ABI. Synthesizable FPGA/ASIC RTL or HLS compilation is a separate unverified goal; LLVM native compilation alone does not generate circuits.

Commonly orchestrates FPGA/ASIC-based devices through external services, ports or native drivers. BEAM application code does not ordinarily synthesize to RTL or gates.Can control FPGA/ASIC devices through MMIO, PCIe, drivers and C interfaces. Specialized HDL/HLS tools are needed to synthesize datapaths; ordinary Rust CPU binaries are not FPGA/ASIC logic.Verilog/SystemVerilog, VHDL and HDL/HLS systems such as Amaranth or vendor tools generate hardware; C/C++ can feed supported HLS workflows.
WebSocket serversDesign / in development

Design: HTTP/WS actors with ownership-aware handoff, backpressure, quotas and supervisor-driven recovery; production capacity not verified.

Cowboy and other BEAM frameworks support large numbers of socket-driven connections with process isolation.Tokio-based stacks such as axum, tokio-tungstenite and Actix Web support high-concurrency WebSockets.Elixir Phoenix Channels, Node.js, Go and Java Netty provide established real-time servers.

Stack tracesDesign / in development

Goal: source-mapped async/actor stack traces with causal message context across AOT/Graal/native boundaries; no uniform verified format.

Process crash reports, stacktraces, logger/SASL and OTP crash diagnostics integrate with supervisors.Backtraces through RUST_BACKTRACE, panic reporting, tracing spans and debugger/profiler integration.JVM/.NET offer mature stack diagnostics; distributed traces require correlation across services.
High load: CPU, memory and profilingResearch / not established

Target: per-actor allocation/arena metrics, CPU profiles, p50/p95/p99 latency, queue depth, GC pauses and L1/L2 locality. No head-to-head throughput, memory or CPU win is established.

Observer, telemetry, tracing and profiling support scheduler utilization, reductions, mailbox growth and process memory analysis; capacity is workload-specific.perf, flamegraphs, tracing, heap profilers and runtime-specific instruments; tuning spans allocator, executor, batching and locking.Go pprof, Java JFR and .NET counters support mature profiling; compare equal workloads on equal hardware.
Concurrency modelDesign / in development

Single-flight, non-reentrant actor turns, structured tasks, channels, explicit suspension and critical state loans are design goals; the advanced task and actor examples remain syntax-only in the pinned browser profile.

Preemptively scheduled BEAM processes communicate via mailboxes; isolated process heaps with no shared mutable Erlang terms by default.OS threads, atomics, scoped threads, async futures and channels; memory safety via Send/Sync and borrow checking.Go goroutines; Java virtual threads; C# async/await and thread pool; JS event loop/workers.
Non-blocking I/O by defaultDesign / in development

Design direction: default evented, backpressured I/O for actor HTTP/TCP/WebSocket and channel operations; blocking foreign calls need isolation or dedicated blocking pools. No universal non-blocking default or cross-backend implementation is verified.

BEAM socket/network I/O integrates with the runtime so Erlang processes can wait without blocking a normal scheduler thread. Blocking NIFs and drivers require dirty schedulers or separate workers; not every foreign call is non-blocking.std file/socket APIs are often blocking unless configured otherwise. Non-blocking I/O and async execution are explicit choices through Tokio, async-std, mio or OS interfaces; async syntax does not make arbitrary FFI non-blocking.Node.js has an event-loop-centric I/O model but synchronous APIs exist; Go uses a netpoller with goroutines; Java has NIO and virtual threads; .NET supports async I/O.
FFI, ABI and C integrationResearch / not established

Goal: explicit C-facing ABI/FFI and safe ownership boundaries, backend-specific native addons and guarded untrusted capabilities; ABI stability not verified.

C NIFs and ports/driver interfaces; NIF mistakes can block schedulers or crash the VM.Stable C ABI interoperability via extern C and #[repr(C)]; Rust ABI itself is not generally stable across versions.Node.js N-API supports native addons; C++ ABI varies; JVM JNI/FFM and .NET P/Invoke bridge native code.

Structured concurrencyDesign / in development

Scoped child tasks, join/cancellation propagation and failure containment are goals; do not infer parity from syntax.

OTP links, monitors and supervisors provide process lifecycle coordination; not the same as lexical task scopes.Scoped threads; async task scopes, cancellation and joins vary by library.Rust and Swift task groups/scopes differ; Kotlin coroutine scopes and Java preview structured concurrency are distinct APIs.
Typed errors and failureBrowser example

Result/Option and ? propagation have admitted browser examples. Failure handling does not eliminate all runtime exceptions.

Run admitted example		Exceptions and tagged return tuples; runtime pattern matches.Result, Option and ?; panic remains possible.Swift throws and Result, Go error values, C# exceptions; no universal absence of runtime errors.
Shared mutable stateBrowser example

A narrow critical state-container example is admitted; this is not proof of fair locks, transitive loan safety or deadlock freedom.

Run admitted example		Process state is conventionally private; ETS provides shared storage.Mutex/RwLock and interior mutability; borrowing rules constrain safe access.Swift actor isolation, Java/C# locks, Go mutexes.
Deadlock preventionResearch / not established

Reject provable unsafe lock/await cycles where possible; no general deadlock-freedom guarantee.

Supervision does not prevent all deadlocks or stalled protocols.Safe Rust does not generally prevent deadlock.Static analysis and runtime detection differ by language and tool.
Durable actors and state persistenceResearch / not established

Durable actor snapshots, replay, crash consistency and schema migration are under development; no production durability claim.

OTP processes are not automatically durable; storage/recovery are application or framework concerns.Persistence via libraries and application design.Orleans provides framework-level grain persistence; storage configuration and semantics matter.
Tracing and observabilityDesign / in development

Explicit AOT-compatible tracing and async/actor context propagation are design goals; no universal automatic instrumentation claim.

OTP telemetry and ecosystem tools; process introspection.Tracing and profiling libraries; instrumentation choices vary.OpenTelemetry SDKs exist across many ecosystems; automatic instrumentation varies.

Design / in development
Documented architecture or implementation direction, without a sufficient public receipt for the full claim here.
Research / not established
